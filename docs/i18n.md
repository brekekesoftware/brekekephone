# i18n

## i18n uses array indexes, not key-value pairs, and the index lookup happens at runtime, not build time

The UI uses the `intl` tagged template, while `src/assets/intl-en.json` and `intl-ja.json` are string arrays, not objects. There is also an `intl-vi.json` sitting in `src/assets/` that is fully wired into the source of the array but currently commented out in `intl-store.ts`; Vietnamese assets exist but the locale is not enabled.

The English text in the code is itself the key. `intl-en.json`/`intl-ja.json` are confirmed plain string arrays (327 entries each, index-aligned). Correction to an old claim: the babel plugin (`intl-babel-plugin.js`) does not convert the tagged template into a numeric array index at build time. What it actually does is rewrite `` intl`...` `` into a call passing the normalized template string itself (not an index). The index lookup happens at runtime, in `stores/intl.ts`'s `compileFn`, via an `enLabelsMapIndex` map (string -> index) built once from `intl-en.json` when the module loads. The plugin's job is purely to normalize/extract the string at build time for the `make intl` extraction step (see below); resolving it to an index is a runtime concern. If you're explaining this system to someone, do not say "converted to an index at build time"; say the plugin passes the normalized string, and a runtime map turns that into an index.

At runtime, placeholder compilation is done with Handlebars (`Handlebars.compile(msg)`, using `{{`/`}}` syntax and `helper-moment` for date/moment helpers), and the compiled function is memoized back into the array slot so it is only compiled once per string. Native code also needs the locale for the incoming call UI and notifications, hence `BrekekeUtils.setLocale`, called from `intl-store.ts`'s `setLocale`. Locale is persisted in `RnAsyncStorage` and falls back to the system locale (`AppleLocale`/`I18nManager.localeIdentifier`) on first run.

The `make intl` build step and `intl-new-en.local.json`: the root `Makefile`'s `intl` target (`cd brekekephone/app && rm -rf intl-new-en.local.json && export EXTRACT_INTL=1 && npx babel src -x .js,.ts,.tsx -d ./build && rm -rf ./build && node ./intl-build`) runs Babel over `src` with `EXTRACT_INTL=1`, which makes `intl-babel-plugin.js` append every normalized `intl`/`intlDebug` template it finds into `intl-new-en.local.json` (deduped, sorted). See [Makefile reference](./makefile-reference.md#intl) for the exact current command. `intl-build.js` then diffs that scratch file against the current `intl-en.json`, reuses old English -> Japanese mappings for strings that did not change, marks new/unmatched strings with a `**TRANSLATE**` prefix in the Japanese array, and overwrites both `intl-en.json` and `intl-ja.json` with the resulting arrays. `intl-new-en.local.json` is a git-ignored (`**/*.local.*`) build artifact, not source; if you see it in your working tree, it is leftover from a `make intl` run, not something to commit or hand-edit.

Adding or changing text requires running `make intl` (from the repo root), then translating the new `**TRANSLATE**`-marked entries in `intl-ja.json`; otherwise the app falls back to the English string. Do not build a dynamic string and pass it into `intl`; the plugin cannot extract it, and there is no matching entry in `enLabelsMapIndex` at runtime either. Editing `intl-en.json` by hand easily desyncs the index from `intl-ja.json`, and that misalignment breaks text in many unrelated places, not just the one just edited. `intlDebug` is for error logs (keeps the English version too), not for UI text. If you ever want to enable Vietnamese, the asset file already exists (`intl-vi.json`); check why it is commented out in `intl-store.ts` before assuming it just needs uncommenting, it may be incomplete or intentionally held back.
